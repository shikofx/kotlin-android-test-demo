[[section-final-problem]]
== Проблема: `final` классы в Kotlin

В Java классы по умолчанию "открыты" для наследования, а в Kotlin — наоборот, по умолчанию `final`.

Mockito по своей природе работает, создавая во время выполнения дочерние классы (прокси) от мокируемых классов. Если класс `final`, от него нельзя унаследоваться, и Mockito "из коробки" не может создать для него мок, выбрасывая ошибку.

[[section-solution-mockito-inline]]
== Решение 1: `mockito-inline`

Это основной и рекомендуемый способ. Зависимость `org.mockito:mockito-inline`, которую мы добавили на втором уроке, активирует механизм, который позволяет Mockito мокировать `final` классы и методы без дополнительных усилий. Вам не нужно ничего делать в коде — просто добавьте зависимость, и проблема будет решена.

[[section-solution-mockito-kotlin]]
== Решение 2: Библиотека `mockito-kotlin`

Эта библиотека, помимо удобных функций-оберток, также помогает решать некоторые проблемы взаимодействия Mockito и Kotlin.

*   **Null-safety:** Стандартные матчеры Mockito, такие как `any()`, могут возвращать `null`, что приводит к ошибкам в non-null типах Kotlin. `mockito-kotlin` предоставляет null-safe версии этих матчеров.
*   **Читаемость:** `whenever(mock.method())` вместо `when(mock.method())` выглядит более естественно в Kotlin.
*   **`argumentCaptor`**: Более удобный синтаксис для `ArgumentCaptor`.

```kotlin
// Mockito
val captor = ArgumentCaptor.forClass(String::class.java)

// mockito-kotlin
val captor = argumentCaptor<String>()
```

**Вывод:** Для комфортной работы с Mockito в Kotlin-проекте всегда используйте связку из трех библиотек: `mockito-core`, `mockito-inline` и `mockito-kotlin`.
