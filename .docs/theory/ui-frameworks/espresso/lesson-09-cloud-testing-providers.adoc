[[section-why-cloud]]
== Зачем нужны облачные провайдеры?

Эмуляторы отлично подходят для быстрой разработки и отладки. Однако они не могут полностью воспроизвести поведение реальных устройств. Проблемы, связанные с особенностями конкретного производителя (Samsung, Xiaomi), версией ОС, нехваткой памяти или качеством сети, часто остаются незамеченными.

Облачные провайдеры (device farms) решают эту проблему, предоставляя доступ к огромному парку реальных физических устройств.

*Преимущества:*

*   **Реальные устройства:** Тестирование на сотнях моделей от разных производителей с разными версиями Android.
*   **Параллелизация:** Возможность запускать тесты одновременно на десятках и сотнях устройств, что кардинально сокращает время выполнения всего набора тестов.
*   **Отсутствие поддержки:** Вам не нужно покупать, настраивать и обслуживать собственный парк устройств.
*   **Богатые отчеты:** Провайдеры автоматически записывают видео выполнения теста, собирают логи (`logcat`, network), делают скриншоты и предоставляют метрики производительности (CPU, память).
*   **Дополнительные возможности:** Симуляция различных геолокаций, состояний сети (3G, 4G, Wi-Fi с потерями), смена языка и т.д.

*Ключевые игроки на рынке:* Sauce Labs, BrowserStack, AWS Device Farm, LambdaTest.

[[section-how-it-works]]
== Как это работает?

Принцип работы с облачными провайдерами обычно следующий:

1.  **Сборка приложения:** Вы собираете ваше приложение (`.apk`) и тестовое приложение (`test.apk`).
2.  **Загрузка в облако:** Собранные `.apk` файлы загружаются в хранилище облачного провайдера.
3.  **Конфигурация запуска:** Вы указываете, на каких устройствах хотите запустить тесты. Это делается с помощью специальных конфигурационных файлов или через API.
4.  **Выполнение тестов:** Облачная платформа устанавливает ваше приложение и тестовый пакет на выбранные реальные устройства и запускает тесты с помощью `AndroidJUnitRunner`.
5.  **Сбор результатов:** Платформа собирает все результаты, логи, видео и предоставляет их в удобном веб-интерфейсе.

Важно понимать, что ваш тестовый код на Espresso (`onView`, `perform`, `check`) **не меняется**. Вся магия происходит на уровне конфигурации сборки и запуска.

[[section-saucelabs-integration]]
== Интеграция с Sauce Labs

В нашем проекте уже заложена подготовка к интеграции с Sauce Labs, о чем говорят переменные `SAUCE_USERNAME` и `SAUCE_ACCESS_KEY`.

Для запуска Espresso-тестов на Sauce Labs обычно используется их специальный Gradle-плагин (`sauce-storage`) и инструмент командной строки (`saucectl`).

=== Пример конфигурации (концептуально)

1.  **Настройка `saucectl`**: Создается конфигурационный файл `config.yml`, в котором описывается, что и где запускать.

[source,yaml]
----
# .sauce/config.yml
apiVersion: v1alpha
kind: espresso
sauce:
  region: us-west-1 # Регион дата-центра Sauce Labs
espresso:
  app: ./app/build/outputs/apk/debug/app-debug.apk
  testApp: ./app/build/outputs/apk/androidTest/debug/app-debug-androidTest.apk
suites:
  - name: "Component UI tests on Google Pixel"
    emulators:
      - name: "Google Pixel 6 Pro GoogleAPI Emulator"
        platformVersions:
          - "12.0"
    testOptions:
      class: "by.pda.demoapp.ui.espresso.CheckoutCompleteFragmentTest" # Можно указать конкретный класс
      tag: "component-ui" # Или запустить тесты по тегу
----

2.  **Запуск из CI**: В CI/CD пайплайне вместо `./gradlew connectedDebugAndroidTest` будет выполняться команда, которая использует `saucectl`.

[source,bash]
----
# Установка saucectl
npm install -g saucectl

# Запуск тестов с использованием переменных окружения
# SAUCE_USERNAME и SAUCE_ACCESS_KEY должны быть установлены в CI
saucectl run
----

Этот подход позволяет полностью отделить логику тестов от инфраструктуры их выполнения, делая ваш CI/CD процесс гибким и мощным.
