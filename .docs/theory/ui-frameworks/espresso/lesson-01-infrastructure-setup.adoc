Прежде чем писать первый UI-тест, крайне важно заложить прочный фундамент. Правильно организованная инфраструктура сэкономит массу времени в будущем, сделает тесты более читаемыми и стабильными.

== Зависимости

Первый шаг — добавление всех необходимых библиотек в файл `app/build.gradle`.

[source,groovy]
----
dependencies {
    // Core JUnit 5 for Android
    androidTestImplementation "org.junit.jupiter:junit-jupiter-api:5.10.2"
    androidTestRuntimeOnly "org.junit.jupiter:junit-jupiter-engine:5.10.2"
    androidTestImplementation "org.junit.jupiter:junit-jupiter-params:5.10.2"

    // AndroidX Test & Espresso
    androidTestImplementation "androidx.test:runner:1.7.0"
    androidTestImplementation "androidx.test:rules:1.7.0"
    debugImplementation "androidx.fragment:fragment-testing:1.7.1" // Для FragmentScenario
    androidTestImplementation "androidx.test.espresso:espresso-core:3.5.0"
    androidTestImplementation "androidx.test.espresso:espresso-contrib:3.5.0"
    androidTestImplementation "androidx.test.espresso:espresso-intents:3.5.0"

    // Для синхронного выполнения LiveData в тестах
    androidTestImplementation "androidx.arch.core:core-testing:2.2.0"

    // Allure
    androidTestImplementation "io.qameta.allure:allure-junit5:2.25.0"
}
----

Также необходимо подключить плагин для поддержки JUnit 5 в файле `build.gradle` на уровне проекта:

[source,groovy]
----
// Top-level build.gradle
buildscript {
    dependencies {
        // ...
        classpath('de.mannodermaus.gradle.plugins:android-junit5:1.10.0.0')
    }
}
----

И применить его в `app/build.gradle`: `apply plugin: "de.mannodermaus.android-junit5"`.

== Кастомный TestRunner для подготовки окружения

Стандартный `AndroidJUnitRunner` просто запускает тесты. Однако в реальных проектах перед запуском теста часто требуется подготовить окружение:

*   Инициализировать базу данных в памяти (`in-memory database`) и разрешить запросы в UI-потоке.
*   Подменить сетевой клиент на `mock`.
*   Инициализировать фреймворк для внедрения зависимостей (Hilt, Koin) с тестовой конфигурацией.

Для этого создается кастомный `TestRunner`, который запускает специальный тестовый класс `Application` перед всеми тестами.

===  *Создайте `TestApp.kt` в `src/androidTest`*:
Этот класс наследуется от основного класса приложения (`MyApplication`) и при старте инициализирует специальную тестовую версию `AppDatabase`.

[source,kotlin]
----
package by.pda.demoapp.android // Важно, чтобы пакет совпадал

import by.pda.demoapp.android.MyApplication
import by.pda.demoapp.android.database.AppDatabase

class TestApp : MyApplication() {
    override fun onCreate() {
        super.onCreate()
        // Инициализируем тестовую версию БД, которая разрешает запросы в UI-потоке
        AppDatabase.getTestInstance(this)
    }
}
----

===  *Создайте `DemoTestRunner.kt` в `src/androidTest`*:
Этот Runner переопределяет стандартное поведение и указывает системе использовать наш `TestApp`.

[source,kotlin]
----
package by.pda.demoapp

import android.app.Application
import android.content.Context
import androidx.test.runner.AndroidJUnitRunner
import by.pda.demoapp.android.TestApp // Импортируем наш TestApp

class DemoTestRunner : AndroidJUnitRunner() {
    override fun newApplication(cl: ClassLoader?, className: String?, context: Context?): Application {
        // Принудительно используем наш TestApp вместо основного MyApplication
        return super.newApplication(cl, TestApp::class.java.name, context)
    }
}
----

===  *Зарегистрируйте `DemoTestRunner` в `app/build.gradle`*:
Это самый важный шаг. Указываем системе сборки, какой Runner использовать для инструментированных тестов.

[source,groovy]
----
android {
    defaultConfig {
        // ...
        testInstrumentationRunner "by.pda.demoapp.DemoTestRunner" // Указываем полное имя нашего раннера
    }
}
----

== Структура пакетов

Правильная организация тестов помогает легко находить нужные классы. Рекомендуется разделять UI-тесты по их назначению, повторяя структуру основного приложения:

----
src/androidTest/java/by/pda/demoapp/
├── DemoTestRunner.kt       // Наш кастомный Runner
└── android
    ├── TestApp.kt          // Наше тестовое приложение
    └── ui
        ├── common          // Общие классы для тестов
        │   ├── test
        │   │   ├── BaseUITest.kt
        │   │   ├── FragmentTest.kt
        │   │   └── ActivityTest.kt
        └── espresso        // Пакет с конкретными тестовыми классами
            └── AboutFragmentLinkTest.kt
----

== Иерархия базовых тестовых классов

Чтобы избежать дублирования кода, полезно создать иерархию базовых классов.

*   `BaseUITest`: Абстрактный класс для общей настройки (например, расширения JUnit 5, обработчики падений).
*   `ActivityTest`: Наследуется от `BaseUITest` и отвечает за запуск и остановку `ActivityScenario`.
*   `FragmentTest`: Наследуется от `BaseUITest` и отвечает за запуск и остановку `FragmentScenario`.

== Расширения и Сценарии

*   *JUnit 5 Extensions*: Используйте расширения для управления жизненным циклом тестов. Например, `InstantExecutionExtension` заставляет `LiveData` выполняться синхронно, что критически важно для стабильности тестов с базой данных.

*   *`FragmentScenario` и `ActivityScenario`*: Это классы из библиотек AndroidX Test, которые являются точкой входа для большинства UI-тестов. Они позволяют запускать компоненты (фрагменты или активити) в контролируемой, изолированной среде.

В наших тестах мы будем использовать `ActivityScenario`, запуская `SplashActivity`, чтобы симулировать полный, реалистичный путь пользователя при запуске приложения. Это делает тесты более надежными, так как они проходят через все экраны инициализации.
