[[section-explicit-waits]]
== Явные ожидания

В публичном API Espresso нет явного ожидания, аналогичного `waitFor()` в Selenium**. Это сделано намеренно и является частью философии фреймворка.

=== "Путь Espresso": Автоматическая синхронизация

Espresso спроектирован так, чтобы избавить вас от необходимости в явных ожиданиях. Его основной принцип — автоматическая синхронизация с UI-потоком.

Когда вы вызываете `onView(...)`, Espresso делает следующее:

1.  Проверяет, свободен ли UI-поток.
2.  Если да, пытается найти `View`, соответствующий вашему матчеру.
3.  Если `View` не найден или не соответствует условию (`isDisplayed()`, `isEnabled()` и т.д.), Espresso **не падает сразу**. Он ждет короткий промежуток времени и повторяет попытку.
4.  Этот цикл повторяется до тех пор, пока не истечет внутренний таймаут. Только после этого тест упадет с ошибкой `NoMatchingViewException` или `AssertionFailedError`.

Таким образом, **сам вызов `onView(...).check(...)` уже является неявным ожиданием** появления и нужного состояния элемента.

=== Когда автоматической синхронизации недостаточно?

Проблемы начинаются, когда изменения в UI вызваны **асинхронными операциями**, которые происходят не в UI-потоке:

*   Сетевые запросы (загрузка данных с сервера).
*   Обращения к базе данных.
*   Длительные вычисления в фоновом потоке.

Espresso ничего не знает об этих фоновых задачах и не будет их ждать. Именно для таких случаев и был создан `IdlingResource`.

=== Способы решения проблемы асинхронности

|===
| Метод | Плюсы | Минусы | Когда использовать

| **Автоматическая синхронизация**
| Встроено в Espresso, ничего не нужно делать.
| Работает только для операций в UI-потоке.
| В 90% случаев для простых тестов.

| **`IdlingResource`**
| **Самый надежный и правильный способ.** Тест ждет ровно столько, сколько нужно.
| Требует написания дополнительного кода и интеграции с логикой приложения.
| Для всех асинхронных операций: сетевые запросы, работа с БД, сложные анимации.

| **Кастомный `waitFor` (polling)**
| Прост в реализации и использовании. Не требует изменения кода приложения.
| **Ненадежен ("flaky").** Тест либо ждет дольше, чем нужно, либо падает, если таймаут слишком мал. Замедляет выполнение тестов.
| В редких случаях, когда `IdlingResource` избыточен, а стандартной синхронизации недостаточно (например, для коротких задержек или простых анимаций).
|===

Этот урок посвящен **`IdlingResource`** — официальному и наиболее надежному способу работы с асинхронными операциями в Espresso.

[[section-sync-problem]]
== Проблема синхронизации

Главное преимущество Espresso — автоматическая синхронизация. Он ждет, пока UI-поток свободен, прежде чем выполнить действие. Однако, эта магия **не работает** для длительных фоновых операций, таких как:

*   Сетевые запросы (Retrofit, Volley).
*   Сложные операции с базой данных.
*   Работа с RxJava, Coroutines или кастомными фоновыми потоками.

В этих случаях UI-поток свободен, но данные еще не загружены. Espresso не будет ждать и выполнит проверку немедленно, что приведет к падению теста.

[source,java]
----
@Test
fun loadingData_showsItOnScreen() {
    // Нажимаем на кнопку, которая запускает сетевой запрос
    onView(withId(R.id.load_data_button)).perform(click())

    // ПРОБЛЕМА: Эта проверка выполнится ДО того, как данные придут из сети.
    // Тест упадет, потому что TextView еще пустой.
    onView(withId(R.id.result_textview)).check(matches(withText("Data from network")))
}
----

== А возможно ли устанавливать значения неявных ожиданий?

Краткий ответ: **Нет, в Espresso нет прямого, "официального" способа установить глобальное значение "неявного ожидания"**, как это делается в Selenium с помощью `driver.manage().timeouts().implicitlyWait()`.

Это сделано намеренно. Философия Espresso заключается в **автоматической синхронизации**. Фреймворк спроектирован так, чтобы "чувствовать" состояние приложения и выполнять действия только тогда, когда основной (UI) поток свободен.

Разработчики Espresso считают, что если вам нужно менять таймауты, то, скорее всего, проблема не в таймауте, а в том, что вы неправильно обрабатываете асинхронные операции (для которых нужно использовать `IdlingResource`).

=== "Скрытый" способ: `IdlingPolicies` (Использовать с осторожностью!)

Несмотря на все вышесказанное, существует "недокументированный" и нерекомендуемый способ повлиять на таймауты Espresso. Он связан с классом `IdlingPolicies`.

Этот класс управляет таймаутами, связанными с ожиданием `IdlingResource` и синхронизацией с UI.

*   `setMasterPolicyTimeout(long, TimeUnit)`: Это главный таймаут. Он определяет, как долго Espresso будет ждать, пока все зарегистрированные `IdlingResource` станут свободными. По умолчанию это значение равно **60 секундам**.
*   `setDynamicIdlingResourceErrorPolicy(long, TimeUnit)`: Определяет, как долго Espresso будет ждать появления `IdlingResource`, если он был зарегистрирован *после* начала асинхронной операции. По умолчанию — **26 секунд**.

Изменение этих значений может помочь в отладке или в очень специфичных случаях, но это считается плохой практикой, так как может сделать тесты медленными и скрыть реальные проблемы синхронизации.

==== Как это выглядит в коде?

Если вы все же решите пойти этим путем, делать это нужно аккуратно, изменяя таймаут только на время выполнения конкретного теста и **обязательно возвращая его к значению по умолчанию** после завершения.

[source,java]
----
import androidx.test.espresso.IdlingPolicies;
import org.junit.jupiter.api.AfterEach;
import org.junit.jupiter.api.BeforeEach;
import java.util.concurrent.TimeUnit;

public class MyTimeoutTest {

    @BeforeEach
    public void setCustomTimeout() {
        // Устанавливаем мастер-таймаут на 15 секунд
        IdlingPolicies.setMasterPolicyTimeout(15, TimeUnit.SECONDS);
    }

    @AfterEach
    public void resetTimeout() {
        // КРАЙНЕ ВАЖНО: возвращаем таймаут к значению по умолчанию!
        IdlingPolicies.setMasterPolicyTimeout(60, TimeUnit.SECONDS);
    }
}
----

[[section-what-is-idling-resource]]
== Решение: `IdlingResource`

`IdlingResource` — это механизм, с помощью которого ваше приложение может сообщить Espresso, что оно занято выполнением фоновой работы. Espresso, в свою очередь, будет ждать, пока приложение не сообщит, что оно снова свободно.

Это простой контракт:

1.  Перед началом фоновой операции приложение "уведомляет" `IdlingResource`, что оно **занято**.
2.  После завершения операции (успешного или нет) приложение уведомляет `IdlingResource`, что оно **свободно**.
3.  Espresso перед каждым действием проверяет все зарегистрированные `IdlingResource` и ждет, пока они все не станут свободными.

[[section-implementing-idling-resource]]
== Реализация и интеграция

Хотя можно реализовать интерфейс `IdlingResource` с нуля, проще всего использовать готовую реализацию — `CountingIdlingResource`. Он работает как счетчик:

*   `increment()`: Увеличивает счетчик (приложение занято).
*   `decrement()`: Уменьшает счетчик (приложение освободилось).

Пока счетчик больше нуля, Espresso будет ждать.

=== Шаг 1: Создание глобального `IdlingResource`

Чтобы тесты и приложение могли общаться через один и тот же `IdlingResource`, его нужно сделать доступным глобально. Самый простой способ — создать синглтон-обертку.

[source,java]
----
// В коде приложения (НЕ в тестах)
object EspressoIdlingResource {

    private const val RESOURCE = "GLOBAL"

    @JvmField
    val countingIdlingResource = CountingIdlingResource(RESOURCE)

    fun increment() {
        countingIdlingResource.increment()
    }

    fun decrement() {
        if (!countingIdlingResource.isIdleNow) {
            countingIdlingResource.decrement()
        }
    }
}
----

=== Шаг 2: Использование в коде приложения

Теперь нужно "обернуть" асинхронную операцию в вызовы `increment()` и `decrement()`.

[source,java]
----
// Пример в репозитории или ViewModel
fun loadDataFromServer(callback: (Result) -> Unit) {
    EspressoIdlingResource.increment() // Сообщаем Espresso: мы заняты!
    api.fetchData { result ->
        callback(result)
        EspressoIdlingResource.decrement() // Сообщаем Espresso: мы закончили!
    }
}
----

=== Шаг 3: Регистрация в тестах

Последний шаг — сказать Espresso, чтобы он следил за нашим `IdlingResource`. Это делается в тестовом классе.

[source,java]
----
import androidx.test.espresso.IdlingRegistry
import org.junit.After
import org.junit.Before

class MyAsyncTest {

    @Before
    fun registerIdlingResource() {
        IdlingRegistry.getInstance().register(EspressoIdlingResource.countingIdlingResource)
    }

    @After
    fun unregisterIdlingResource() {
        IdlingRegistry.getInstance().unregister(EspressoIdlingResource.countingIdlingResource)
    }

    @Test
    fun loadingData_showsItOnScreen() {
        // Теперь этот тест будет работать!
        onView(withId(R.id.load_data_button)).perform(click())
        onView(withId(R.id.result_textview)).check(matches(withText("Data from network")))
    }
}
----

Теперь Espresso будет терпеливо ждать завершения сетевого запроса, прежде чем выполнить проверку, и тест станет стабильным.
