[[section-what-is-tdd]]
== Что такое Test-Driven Development (TDD)?

**TDD (Разработка через тестирование)** — это методология разработки, при которой тесты пишутся *до* написания кода основной функциональности.

Цикл TDD состоит из трех шагов:

1.  **Красный (Red):** Написать тест для еще не существующей функциональности. Запустить его и убедиться, что он падает (потому что функциональности еще нет).
2.  **Зеленый (Green):** Написать минимально необходимый код, чтобы тест прошел. На этом этапе не нужно думать об идеальной архитектуре, главная цель — сделать тест "зеленым".
3.  **Рефакторинг (Refactor):** Улучшить написанный код (убрать дублирование, улучшить читаемость), убеждаясь, что тесты по-прежнему проходят.

[[section-tdd-for-ui]]
== Применение TDD для UI-тестирования

Хотя TDD чаще ассоциируется с Unit-тестами, его принципы можно применять и для UI-тестирования с Kaspresso. Это помогает четко определить требования к UI до начала его реализации.

=== Пример: Добавление кнопки "Выход"

Предположим, нам нужно добавить кнопку "Выход" на экран каталога продуктов.

**Шаг 1: Красный (Пишем падающий тест)**

Сначала мы пишем тест, который ищет еще не существующую кнопку и пытается на нее нажать.

```kotlin
@Test
fun logoutButton_shouldReturnToLoginScreen() = run {
    // Сначала логинимся, чтобы попасть на экран каталога
    // ...

    step("When: Пользователь нажимает кнопку 'Выход'") {
        ProductCatalogScreen {
            logoutButton.click() // Кнопка еще не существует, тест упадет здесь
        }
    }
    step("Then: Пользователь должен вернуться на экран входа") {
        LoginScreen {
            loginButton.isDisplayed()
        }
    }
}
```

Мы запускаем этот тест и получаем `ElementNotFoundException`. Это "красный" этап.

**Шаг 2: Зеленый (Пишем минимальный код)**

Теперь разработчик добавляет кнопку `logoutButton` в XML-разметку и реализует минимальную логику в `ProductCatalogFragment`, чтобы по клику на нее происходил переход на `LoginActivity`.

После этого мы снова запускаем наш тест. Теперь он должен пройти. Это "зеленый" этап.

**Шаг 3: Рефакторинг**

Разработчик может улучшить код (например, вынести логику выхода в отдельный `UseCase`), а мы можем улучшить наш тест (например, вынести логику логина в отдельный метод в `KTestCase`). После каждого изменения мы снова запускаем тесты, чтобы убедиться, что ничего не сломалось.

Применение TDD к UI-тестам помогает создавать функциональность, которая с самого начала соответствует ожиданиям и покрыта тестами.
